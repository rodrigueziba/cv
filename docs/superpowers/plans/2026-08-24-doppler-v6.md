## Design decisions made while writing this plan (read first)

1. **Corridor audio override (Modificación 6) is reversible** — confirmed directly with the user via AskUserQuestion: crossing back below 50% restores whatever was playing before (file track / tone / arpeggio, including its specific frequency or key), crossing forward past 50% again re-triggers `audio4.mp3`.
2. **`pared.jpg` wall texture defaults ON** (Modificación 7's own wording — "una opción... para desactivar este cambio" — describes the toggle as an opt-out, so the new behavior is the default) — a new debug-menu boolean, default `true`.
3. **JSON text content (Modificación 4) covers text only, not styling** — `TEXT_BLOCKS`/`CORRIDOR_TEXT_BLOCKS`' existing per-block styling/timing config (font size, shadow, position, startInstance) stays in TypeScript; only the actual line/sentence content moves into the JSON file, keyed by block id and by platform (`pc`/`mobile`). The JSON initially contains IDENTICAL content for both platforms (the infrastructure is what's being built — diverging the copy itself is left for the user to edit later, not invented here).
4. **JSON file location:** `content/textBlocks.json` at the repo root — a clearly separate, discoverable location outside `app/`, matching "fácilmente ubicable... para cargar y editar."
5. **Corrección 1 (fingerprint icon "cut in half") root cause identified by direct inspection**, not guessed: the existing `FINGERPRINT_SVG_PATHS` only draw the upper ~66% of the icon's 0–100 viewBox (arcs spanning y=16–82, open at the bottom with no closing curve) — a genuinely incomplete shape, not a CSS clipping bug. Fixed by redrawing the paths to span the full viewBox with a more complete taper.
6. **Corrección 2 (landscape steering) root cause is a fragile detection API, not the axis-remap math itself** — the remap function (`remapDeviceTiltToScreenAxes`, added in a prior plan) is mathematically correct and unit-tested, but the ANGLE it's fed (`screen.orientation?.angle ?? window.orientation ?? 0`) may not be read correctly on the user's actual device: `window.orientation` is a deprecated API removed on some modern mobile browsers, and reliance on the exact numeric angle convention is fragile across vendors. Replaced with `screen.orientation?.type` string matching (`'landscape-primary'`/`'landscape-secondary'`), which is more consistently implemented, with `matchMedia('(orientation: landscape)')` as an ultimate boolean fallback if `screen.orientation` is unavailable at all (in which case direction can't be determined and portrait's mapping is used as a safe default, documented as a known residual limitation on that rare fallback path).
7. **Modificación 5 (corridor entry framing) is implemented as a clamp, not a global re-tune** — `CORRIDOR_CONFIG.chaseDistanceMultiplier`/`chaseHeightMultiplier` were carefully tuned across 4 rounds of visual QA in an earlier plan; this task does not touch them. Instead, the chase camera's Z position is clamped to never sit behind (outside) the tunnel entrance plane, which only affects the first few moments of the corridor phase (while the sphere is still near the entrance) and leaves the already-tuned steady-state chase framing completely unchanged once the sphere has traveled further in.
8. **Modificación 2 (PC click → scroll hint) is additive to the existing scroll-progress-driven fade**, not a replacement — a click starts a 3-second "forced visible" window with its own fade-out; once that window expires, the indicator's opacity reverts to whatever the normal scroll-progress formula would already give it (so scrolling further during or after the click-triggered window still behaves exactly as before).

## Task 9: Mobile landscape — more robust orientation detection for device-tilt steering

**Files:**
- Modify: `app/components/Section1.tsx`

**What's requested:** Corrección 2 — landscape steering still behaves like portrait on the user's real device, despite the axis-remap function itself being correct and unit-tested (confirmed in a prior plan's review). Root cause per Design Decision 6: the ANGLE-reading APIs (`screen.orientation.angle`, `window.orientation`) are unreliable across mobile browsers. Switch to `screen.orientation.type` string matching, the more consistently implemented API.

- [ ] **Step 1: Replace the angle-based detection**

Find `onDeviceOrientation` (search for it). It currently computes:
```ts
      const screenAngle =
        screen.orientation?.angle ?? (window as unknown as { orientation?: number }).orientation ?? 0;
      const { x: sx, y: sy } = remapDeviceTiltToScreenAxes(e.beta ?? 0, e.gamma ?? 0, screenAngle);
```
Replace with:
```ts
      // screen.orientation.angle / the legacy window.orientation are
      // unreliable across mobile browsers (window.orientation is removed
      // on some modern engines entirely; angle-degree conventions aren't
      // fully consistent either) — screen.orientation.type is a string
      // enum ('portrait-primary' | 'portrait-secondary' |
      // 'landscape-primary' | 'landscape-secondary') that's more
      // consistently implemented. Falls back to matchMedia's boolean
      // portrait/landscape check (which IS universally reliable) if
      // screen.orientation itself is unavailable — in that fallback case
      // rotation DIRECTION can't be determined, so portrait's mapping
      // (angle 0) is used as a safe default; this is a known, documented
      // residual limitation on that specific fallback path, not
      // something this fix claims to fully solve.
      const orientationType = screen.orientation?.type;
      let screenAngle = 0;
      if (orientationType === 'landscape-primary') screenAngle = 90;
      else if (orientationType === 'landscape-secondary') screenAngle = -90;
      else if (!orientationType && window.matchMedia('(orientation: landscape)').matches) {
        screenAngle = 90; // direction unknown — best-effort guess, see comment above
      }
      const { x: sx, y: sy } = remapDeviceTiltToScreenAxes(e.beta ?? 0, e.gamma ?? 0, screenAngle);
```
